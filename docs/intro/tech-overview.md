# 기술 스택 요약

이 문서는 Entity Server의 기술 구성을 빠르게 이해하기 위한 소개 문서입니다.

## 한 줄 요약

Entity Server는 **Go 기반 단일 바이너리 서버** 위에 **엔티티 중심 API/스키마 운영**, **보안 기능**, **운영 자동화**를 통합한 백엔드 런타임입니다.

## 핵심 기술 구성

- **런타임**: Go + Fiber 기반 고성능 HTTP 서버
- **데이터 계층**: MySQL/MariaDB/TiDB/PostgreSQL/SQLite/MSSQL 및 선택형 DataStore
- **보안**: JWT, API Key/HMAC, RBAC, OAuth 2.0, XChaCha20-Poly1305 기반 암호화 옵션
- **운영 기능**: 이력/리비전, 롤백, 엔티티 동기화, 관리 스크립트
- **확장 기능**: 파일 스토리지, SMTP, SMS, 카카오 알림톡, Push, 백업, 소셜 로그인
- **연동 모델**: 프론트엔드 직결 또는 API 게이트웨이 분리(게이트웨이는 비즈니스 로직 중심으로 경량화)

## 운영 모델 비교 (BaaS vs 온프레미스)

| 항목             | BaaS(완전 관리형)          | 온프레미스/자체 운영(Entity Server 성향) |
| ---------------- | -------------------------- | ---------------------------------------- |
| 운영 방식        | 서비스형(공급자 관리)      | 조직 직접 운영                           |
| 인프라 접근성    | 제한적                     | 네트워크/보안/배포 경로까지 제어 가능    |
| 도입 속도        | 빠름                       | 환경 준비 필요                           |
| 장기 운영 유연성 | 플랫폼 정책 의존           | 내부 표준에 맞춘 확장 용이               |
| 적합한 경우      | 빠른 MVP, 운영 단순화 우선 | 보안·감사·망분리·커스터마이징 우선       |

## 유사 API 백엔드와의 관점 차이

비슷한 기능(API, 인증, 데이터 접근)을 제공해도 실제 선택 기준은 다음이 갈립니다.

- **운영 통제 수준**: 관리형 서비스 중심인지, 자체 운영 중심인지
- **기본 제공 우선순위**: 실시간/콘텐츠/내부업무 표준화 중 무엇이 핵심인지
- **도입 이후 변화 비용**: 스키마 변경, 권한 정책, 감사 대응을 얼마나 자주 수행하는지

## Entity Server 고유 핵심 기능

| 핵심 기능                                     | 설명                                                          | 실무 의미                                        |
| --------------------------------------------- | ------------------------------------------------------------- | ------------------------------------------------ |
| 엔티티 JSON 기반 스키마+API 동시 운영         | 엔티티 정의만으로 테이블/CRUD/API 반영 흐름을 단순화          | 코드 작성량을 줄이고 변경 반영 속도를 높임       |
| 이력·리비전·롤백 내장                         | 변경 이력 추적과 롤백을 운영 기능으로 기본 제공               | 장애/오입력 복구와 감사 대응이 쉬움              |
| 단일 바이너리 중심 배포                       | 서버 구성요소를 단일 실행 단위로 운영 가능                    | 배포/업데이트 절차가 단순하고 운영 편차가 줄어듦 |
| 권한 체계 기본 제공 (RBAC/JWT/HMAC/OAuth 2.0) | 인증/인가를 옵션 조합으로 적용 가능                           | 서비스 성격에 맞춘 보안 정책 적용이 쉬움         |
| XChaCha20-Poly1305 암호화 옵션                | 데이터/패킷 암호화를 설정으로 활성화 가능                     | 민감 데이터 보호 수준을 높이고 규정 대응에 유리  |
| 확장 기능 옵션형 활성화                       | 파일/SMTP/SMS/알림톡/Push/백업 등을 필요 시 단계적으로 활성화 | 초기 단순 운영 후 요구 증가에 맞춰 확장 가능     |

## 배포 관점 장점

- **단순 배포**: 단일 바이너리 중심 운영으로 배포 절차 단순화
- **빠른 변경 반영**: 엔티티/설정 기반 운영으로 반복 개발 비용 절감
- **운영 안정성**: 권한/감사/이력 기능을 기본 제공
- **확장 유연성**: 기능을 설정 기반으로 단계적으로 활성화
- **유틸리티 연동 용이성**: 스토리지·백업·훅 같은 유틸리티도 간단한 설정만으로 빠르게 연결
- **개발 집중 목표**: 알림·메일·인증·(향후)결제 같은 공통 기능은 플랫폼에 맡기고 도메인 로직 구현에 집중

## 확장 로드맵

- 현재는 인증/알림/백업/스토리지 등 공통 기능을 설정 기반으로 제공
- 향후 PG 결제 연동까지 설정 기반 확장 범위를 넓히는 방향으로 발전 예정

## 보안 관점 포인트

- 인증 체계를 환경/서비스 특성에 맞게 선택 가능 (JWT, HMAC, OAuth 2.0)
- 역할 기반 권한 제어(RBAC)로 API 접근 범위 제한
- XChaCha20-Poly1305 기반 데이터/패킷 암호화 옵션으로 민감 데이터 보호 수준 강화

## 아키텍처를 볼 때 체크할 것

- 현재 서비스가 CRUD 중심인지, 실시간/이벤트 중심인지
- 권한·감사·이력 관리가 필수 요구인지
- 기존 DB를 그대로 활용해야 하는지
