# 금융권 수준에 버금가는 보안 설계 포지셔닝

Entity Server는 특정 금융 보안 인증을 획득했거나, 금융권 규제 준수를 자동으로 보장하는 제품이라고 표현하지 않습니다. 대신 금융권 시스템이 중요하게 보는 핵심 보안 요구, 즉 **전송 보호, 저장 데이터 보호, 요청 무결성, 권한 분리, 감사 추적, 운영 통제**를 제품 구조 안에 기본 계층으로 갖추는 것을 목표로 합니다.

따라서 가장 정확한 표현은 다음과 같습니다.

> Entity Server는 금융권에서 요구하는 보안 통제 관점에 버금가는 다층 방어 구조를 제공하는 엔터프라이즈급 백엔드 런타임입니다.

이 문서는 Entity Server의 보안 구조를 금융권 시스템에서 흔히 요구하는 보안 관점과 비교하여, 어떤 점을 자신 있게 강조할 수 있고 어떤 표현은 피해야 하는지 정리합니다.

---

## 핵심 메시지

Entity Server의 강점은 단일 암호화 알고리즘 하나가 아니라 **여러 보안 계층이 서로 다른 실패 지점을 막도록 설계되어 있다는 점**입니다.

| 보안 관점        | Entity Server 제공 기능                             | 강조 포인트                                                   |
| ---------------- | --------------------------------------------------- | ------------------------------------------------------------- |
| 전송 구간 보호   | HTTPS/TLS 병행 사용 + 선택형 패킷 암호화            | TLS 위에 애플리케이션 레벨 암호화 계층을 추가할 수 있음       |
| 요청 위변조 방지 | API Key + HMAC-SHA256 서명                          | 요청 본문, 경로, 시각, nonce를 묶어 변조와 재전송 공격을 줄임 |
| 저장 데이터 보호 | XChaCha20-Poly1305 기반 DB data blob 암호화         | DB 직접 접근 또는 백업 파일 유출 시 민감 본문 노출을 줄임     |
| 사용자 인증      | JWT Access/Refresh 토큰                             | 사용자 세션과 서버 간 API 키 인증을 분리 운영 가능            |
| 권한 분리        | RBAC 역할/권한 체계                                 | API 키와 사용자 역할별 접근 범위를 세분화 가능                |
| 감사/추적        | history/revision/transaction_id                     | 데이터 변경 이력을 자동 기록하고 특정 시점 복원 가능          |
| 운영 통제        | 단일 바이너리, 설정 파일, 스크립트, 온프레미스 운영 | 조직의 망분리, 키 관리, 배포 정책에 맞춰 운영 가능            |

## 금융권 보안 요구와의 비교

금융권 보안은 특정 알고리즘 하나보다 **통제 체계 전체**를 봅니다. 암호화, 인증, 권한, 로그, 키 관리, 배포 통제, 장애 대응이 함께 맞물려야 합니다.

| 금융권에서 중요하게 보는 항목 | Entity Server의 대응                                   | 비고                                                |
| ----------------------------- | ------------------------------------------------------ | --------------------------------------------------- |
| 통신 구간 암호화              | HTTPS/TLS 사용 전제, 추가로 요청/응답 패킷 암호화 지원 | TLS를 대체하지 않고 보완 계층으로 동작              |
| 전문 또는 API 위변조 방지     | HMAC-SHA256 서명 검증                                  | method/path/timestamp/nonce/body 기반 검증          |
| 재전송 공격 방지              | `X-Nonce`, timestamp skew, nonce 저장소                | 프로덕션 다중 인스턴스는 Redis/Memcache 저장소 권장 |
| 중요 데이터 저장 암호화       | XChaCha20-Poly1305 DB blob 암호화                      | 검색용 index 필드는 별도 설계 필요                  |
| 비밀번호/비밀값 단방향 처리   | `hash: true` 필드의 SHA-256 해시 저장                  | 복원이 필요 없는 값에 적용                          |
| 권한 최소화                   | RBAC 권한 매핑                                         | API 키/역할별 API 접근 범위 제한                    |
| 사용자 세션 통제              | JWT Access/Refresh 토큰, revoke 흐름                   | 브라우저 직접 통신 시 CSRF 보호와 함께 사용         |
| 감사 로그                     | entity history, revision, rollback                     | 변경 후 스냅샷과 transaction_id 기반 추적           |
| 백업 보호                     | 암호화된 data 유지, 백업 파일 AES-256-GCM 옵션         | 백업 저장소 정책과 함께 운영                        |
| 온프레미스/망분리 운영        | 자체 서버, 자체 DB, 단일 바이너리 배포                 | 금융권형 폐쇄망/전용망 운영 모델과 궁합이 좋음      |

이 비교에서 중요한 점은 “금융권 인증을 받았다”가 아니라, **금융권 시스템이 보는 보안 체크리스트와 같은 방향의 방어 수단을 제품 구조에 포함한다**는 것입니다.

## 암호화 알고리즘 포지셔닝

Entity Server는 데이터와 패킷 보호에 **XChaCha20-Poly1305**를 사용합니다. 이 알고리즘은 현대적인 AEAD(Authenticated Encryption with Associated Data) 계열로, 암호화와 무결성 검증을 함께 제공합니다.

다만 “금융권 표준 알고리즘”이라고 표현하는 것은 피하는 편이 안전합니다. 금융권에서 실제로 요구하는 알고리즘과 인증 기준은 국가, 기관, 망 구간, 시스템 분류에 따라 다를 수 있기 때문입니다.

대신 다음처럼 표현할 수 있습니다.

| 피해야 할 표현                   | 권장 표현                                        |
| -------------------------------- | ------------------------------------------------ |
| 금융권 인증 암호화 알고리즘 사용 | 현대적인 AEAD 암호화 알고리즘을 사용             |
| 금융권 보안 인증 완료            | 금융권 보안 요구에 가까운 다층 통제 구조 제공    |
| TLS보다 안전함                   | TLS 위에 애플리케이션 레벨 보호 계층을 추가 가능 |
| 완벽한 데이터 보호               | DB/네트워크/백업 유출 시 평문 노출 가능성을 줄임 |

### 왜 XChaCha20-Poly1305인가

- **기밀성 + 무결성 동시 제공**: 암호문이 변조되면 Poly1305 태그 검증에서 실패합니다.
- **긴 nonce**: 24바이트 nonce를 사용해 대량 요청에서도 nonce 충돌 위험을 낮춥니다.
- **성능과 구현 안정성**: 서버와 클라이언트에서 비교적 빠르게 처리할 수 있고, 모바일/웹/서버 환경에서 구현 부담이 낮습니다.
- **TLS 보완에 적합**: TLS 종료 지점 이후에도 애플리케이션 바디를 별도 암호문으로 유지할 수 있습니다.

## Entity Server의 다층 방어 구조

Entity Server의 보안 구조는 다음처럼 겹겹이 적용됩니다.

```text
Client / Service
  |
  | HTTPS/TLS
  v
HMAC 또는 JWT 인증
  |
  | timestamp + nonce + signature 검증
  v
RBAC 권한 검증
  |
  | entity/action 단위 접근 제어
  v
Handler / Service
  |
  | 요청 처리, 트랜잭션 ID, 변경 이력 기록
  v
DB data blob 암호화
  |
  | XChaCha20-Poly1305
  v
History / Backup / Rollback
```

패킷 암호화를 활성화하면 인증된 요청/응답 바디에도 애플리케이션 레벨 암호화가 추가됩니다.

```text
HTTPS/TLS
  + HMAC/JWT 인증
  + RBAC 인가
  + XChaCha20-Poly1305 패킷 암호화
  + XChaCha20-Poly1305 DB 저장 암호화
  + History/Audit 추적
```

이 구조는 금융권 시스템에서 흔히 말하는 “단일 방어선에 의존하지 않는 구조”와 방향이 같습니다.

## 보안 사고 시나리오별 방어 포인트

| 시나리오         | 일반적인 위험                 | Entity Server 방어 포인트                                 |
| ---------------- | ----------------------------- | --------------------------------------------------------- |
| 네트워크 스니핑  | API 응답 본문 노출            | TLS + 패킷 암호화 활성 시 바디가 추가 암호문으로 보호됨   |
| 요청 재전송      | 같은 요청 반복 실행           | HMAC timestamp + nonce 검증으로 재전송 공격을 줄임        |
| 요청 본문 변조   | 금액/상태/권한 필드 조작      | HMAC 서명 불일치로 차단 가능                              |
| API 키 권한 과다 | 키 하나 유출 시 전체 API 접근 | RBAC 역할로 API 키별 권한 범위 제한 가능                  |
| DB 직접 조회     | 민감 data 컬럼 평문 노출      | data blob 암호화로 본문 평문 노출을 줄임                  |
| 백업 파일 유출   | 백업에 민감 데이터 포함       | 암호화된 data 유지 + 백업 파일 AES-256-GCM 옵션 사용 가능 |
| 운영자 실수      | 잘못된 데이터 수정/삭제       | history/revision/rollback으로 변경 추적 및 복구 가능      |
| 다중 테넌트 혼선 | 다른 라이선스 데이터 접근     | license scope와 인증 컨텍스트 기반 데이터 범위 제어 가능  |

## 마케팅 문구 예시

아래 문구는 기술적으로 방어 가능한 표현입니다.

### 짧은 소개 문구

> Entity Server는 HMAC 서명, RBAC, JWT, XChaCha20-Poly1305 암호화, 이력 추적을 조합해 금융권 보안 요구에 버금가는 다층 방어 구조를 제공하는 엔터프라이즈 백엔드입니다.

### 제품 소개 문구

> 금융권 시스템이 중요하게 보는 것은 단순한 암호화 알고리즘 하나가 아니라, 전송 구간 보호·저장 데이터 보호·요청 무결성·권한 분리·감사 추적이 함께 작동하는 통제 구조입니다. Entity Server는 HMAC-SHA256 요청 서명, nonce 기반 재전송 방지, RBAC 권한 제어, JWT 인증, XChaCha20-Poly1305 기반 데이터/패킷 암호화, history/revision 기반 감사 추적을 하나의 서버 런타임에 통합합니다.

### 보수적인 제안서 문구

> Entity Server는 금융권 인증 제품임을 주장하지 않습니다. 다만 금융권 수준 시스템에서 요구되는 주요 보안 통제 항목과 비교했을 때, 인증·인가·암호화·감사·운영 통제 측면에서 그에 준하는 보안 설계를 적용할 수 있는 구조를 제공합니다.

### 강하게 어필하는 문구

> TLS만으로 전송 구간을 보호하는 수준을 넘어, 요청 서명·nonce·RBAC·패킷 암호화·DB 암호화·변경 이력 추적을 겹겹이 적용할 수 있습니다. Entity Server는 내부 업무 시스템, 폐쇄망, 민감 데이터 API처럼 높은 통제가 필요한 환경에서 금융권급 설계 원칙에 가까운 보안 모델을 제공합니다.

## 표현 가이드

### 사용하기 좋은 표현

- 금융권 보안 요구에 버금가는 다층 방어 구조
- 금융권형 보안 통제 관점에 맞춘 설계
- 엔터프라이즈급 인증·인가·암호화·감사 기능
- TLS 위에 애플리케이션 레벨 암호화를 추가하는 구조
- 저장 데이터와 전송 데이터를 분리 보호하는 구조
- 요청 무결성, 재전송 방지, 권한 분리, 이력 추적을 통합 제공

### 피하는 편이 안전한 표현

- 금융권 인증 완료
- 금융보안원 인증 알고리즘 사용
- 금융권 표준 암호화 제품
- 100% 안전
- TLS보다 안전
- 규제 준수 자동 보장

## 권장 운영 조합

높은 보안 수준을 강조하려면 기능이 존재한다는 설명만으로는 부족합니다. 아래 설정 조합을 운영 표준으로 권장하는 편이 좋습니다.

| 영역         | 권장 설정                                                                                |
| ------------ | ---------------------------------------------------------------------------------------- |
| 전송         | HTTPS/TLS 필수                                                                           |
| 서버 간 통신 | `enable_hmac: true`                                                                      |
| 권한         | `enable_rbac: true`, 최소 권한 역할 구성                                                 |
| 패킷 암호화  | 프로덕션에서 `enable_packet_encryption: true` 검토                                       |
| 저장 암호화  | `enable_data_encryption: true` 유지                                                      |
| nonce 저장소 | 다중 인스턴스에서는 Redis 또는 Memcache 사용                                             |
| 키 관리      | `ENCRYPTION_KEY`, `JWT_SECRET`, HMAC secret은 시크릿 매니저 또는 안전한 환경 변수로 관리 |
| 백업         | 백업 압축 + 암호화 + 외부 저장소 접근 제한                                               |
| 감사         | history/revision 유지, 운영자 계정 분리                                                  |

## 결론

Entity Server를 “금융권 인증 제품”이라고 말할 수는 없습니다. 하지만 금융권 시스템이 중요하게 보는 보안 통제 관점, 즉 **암호화, 요청 무결성, 재전송 방지, 권한 분리, 감사 추적, 운영 통제**를 제품 레벨에서 함께 제공한다는 점은 충분히 강하게 말할 수 있습니다.

가장 좋은 포지셔닝은 다음 한 문장입니다.

> Entity Server는 금융권 보안 인증을 주장하지 않지만, 금융권 수준 시스템에서 요구되는 핵심 보안 통제에 버금가는 다층 방어 구조를 제공하도록 설계되었습니다.
