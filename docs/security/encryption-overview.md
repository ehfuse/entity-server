## 1) 한 줄 요약

> **XChaCha20-Poly1305**라는 암호 방식으로
> (1) 데이터베이스에 저장되는 내용을 **가맹점별로 다른 열쇠**를 써서 암호화하고,
> (2) 사용자 화면과 서버가 주고받는 내용을 **로그인할 때 만들어진 열쇠**로 한 번 더 암호화합니다.
>
> 속도 저하는 사용자가 체감할 수 없는 수준이며, 특수한 하드웨어 없이도 빠르다는 점이 이 방식을 고른 이유입니다.

---

## 2) 어떤 알고리즘을 쓰는가

**XChaCha20-Poly1305** — 흔히 말하는 "ChaCha20-Poly1305"의 확장판입니다.

| 구성 요소     | 역할                              | 비유                    |
| ------------- | --------------------------------- | ----------------------- |
| **XChaCha20** | 내용을 알아볼 수 없게 섞음        | 편지를 암호문으로 바꿈  |
| **Poly1305**  | 위·변조 여부를 검증하는 확인 표식 | 봉투에 붙인 봉인 스티커 |

이렇게 **감추기와 봉인 검사를 한 번에** 처리하는 방식을 **인증된 암호화**라고 부릅니다.
누군가 중간에서 값을 단 한 글자라도 바꾸면 **복원 자체가 실패**합니다.
즉 "몰래 숫자만 바꿔치기"가 원천적으로 불가능합니다.

### 앞의 `X`는 무슨 뜻인가

암호화할 때마다 함께 쓰는 **1회용 난수**의 길이를 두 배로 늘렸다는 뜻입니다.

- 짧은 난수를 쓰면, 한 열쇠로 수억 건을 암호화하다 보면 **같은 난수가 우연히 재사용될** 위험이 있습니다.
- 난수가 겹치면 암호가 약해집니다. 확장판은 난수 공간이 압도적으로 넓어 **그냥 매번 무작위로 뽑아도 실질적으로 겹치지 않습니다.**
- 데이터가 수억 건 쌓이는 데이터베이스 암호화에서 이 차이가 결정적입니다.

### 신뢰할 수 있는 방식인가

국제 인터넷 표준(IETF RFC 8439)으로 규격이 공개되어 있고,
보안 메신저 **Signal**, VPN 프로그램 **WireGuard**, **구글의 모바일 통신 암호**가 모두 같은 계열을 사용합니다.
새로 만든 방식이 아니라, 전 세계에서 검증된 방식을 그대로 채택한 것입니다.

## 3) 두 계층의 암호화

| 계층                 | 무엇을 암호화하나            | 무엇을 막아주나                     |
| -------------------- | ---------------------------- | ----------------------------------- |
| **DB 데이터 암호화** | 데이터베이스에 저장되는 내용 | DB 파일이나 백업이 통째로 유출될 때 |
| **패킷 암호화**      | 화면과 서버가 주고받는 내용  | 통신 엿보기, 자동 수집 프로그램     |

### 3.1 DB 데이터 암호화

**"데이터베이스를 통째로 훔쳐가도 읽을 수 없게 한다"** 가 목표입니다.

Entity Server는 이름·연락처 같은 항목을 칸마다 나눠 저장하지 않고,
한 건의 데이터를 **통째로 암호화해 하나의 덩어리로** 저장합니다.
따라서 DB 관리 도구로 직접 열어봐도 알아볼 수 없는 문자열만 보입니다.

**적용 대상**

- 모든 데이터의 본문
- 암호화 대상으로 지정한 검색용 항목
- **업로드된 파일** 자체
- 변경 이력 기록
- 가맹점 정보(그 안에 든 열쇠 포함)

**가맹점별 열쇠 분리**

가맹점 단위로 관리되는 데이터는 **그 가맹점 전용 열쇠**로, 시스템 공통 데이터는 별도의 마스터 열쇠로 암호화합니다.
따라서 **A 가맹점의 열쇠가 유출되어도 B 가맹점 데이터는 열리지 않습니다.**

**검색은 어떻게 되나**

같은 "홍길동"이라도 저장될 때마다 **매번 다른 암호문**이 됩니다. 같은 값이 같은 모양으로 쌓이면
그 규칙만으로도 내용을 추측할 수 있기 때문에, 일부러 매번 다르게 만듭니다.
대신 그만큼 **암호문끼리 맞대어 보는 방식의 검색은 성립하지 않습니다.**

그래서 이름·연락처처럼 검색이 필요한 항목은 **검색 전용 표식을 따로 만들어 함께 저장**합니다.
이 표식은 되돌려 읽을 수 없는 형태라 그 자체로는 개인정보가 되지 않으면서, 찾는 값과 대조하는 용도로는 쓸 수 있습니다.
사용자 입장에서 검색 기능은 평소와 똑같이 동작합니다.

### 3.2 패킷 암호화

> **잠깐 — TLS(HTTPS)가 무엇인가요?**
>
> 브라우저 주소창에 보이는 **자물쇠 아이콘**이 바로 그것입니다.
> TLS는 브라우저와 서버 사이 **오가는 구간**을 통째로 암호화하는 인터넷 표준 규약이고,
> 여기에 웹 통신(HTTP)을 얹은 것이 **HTTPS**입니다.
> 카페 와이파이처럼 중간에서 누가 통신을 엿보더라도 내용을 알 수 없게 해줍니다.
>
> 다만 TLS에는 두 가지 빈틈이 있습니다.
>
> - **서버에 도착하는 순간 풀립니다** → 저장된 데이터는 전혀 보호하지 못합니다
> - **정상적으로 로그인한 상대는 그대로 통과합니다** → 자동 수집 프로그램(크롤러)을 막지 못합니다
>
> 이 문서의 두 암호화는 정확히 그 빈틈을 메우는 장치입니다.

패킷 암호화는 HTTPS 위에 **한 겹 더** 씌우는 방어층입니다.
주고받는 내용 전체가 사람이 읽을 수 없는 **바이너리 덩어리**로 오가기 때문에,
통신을 가로채 저장하더라도 목록이나 개인정보를 뽑아낼 수 없습니다.

여기에 두 가지 설계 장치가 있습니다.

1. **열쇠를 주고받지 않습니다.**
   로그인할 때 발급된 인증 정보로부터 **서버와 사용자 화면이 각자 똑같은 열쇠를 계산해냅니다.**
   열쇠가 네트워크를 타고 흐르지 않으므로, 열쇠를 가로챌 구간 자체가 존재하지 않습니다.

2. **봉투의 모양조차 매번 달라집니다.**
   암호문 앞에 붙는 무작위 머리글의 **길이가 열쇠에 따라 달라집니다.**
   즉 열쇠를 모르면 어디부터가 진짜 내용인지조차 알 수 없어, 해독 시도의 출발점 자체가 막힙니다.

**운영 편의를 위한 예외**

- 오류 응답은 평문 그대로 유지 — 장애 파악·모니터링에 지장 없음
- 로그인 없이 누구나 보는 공개 페이지는 대상에서 제외
- 암호화를 꺼두면 겉보기에 평범한 일반 서버와 구별되지 않음

## 4) 키는 어떻게 만들어지는가

원본 열쇠를 **그대로 쓰지 않습니다.** 용도마다 원본에서 별도의 열쇠를 새로 만들어 씁니다.

| 용도                       | 어디서 만들어지나            |
| -------------------------- | ---------------------------- |
| DB 데이터 암호화           | 마스터 열쇠 또는 가맹점 열쇠 |
| 통신 암호화(로그인 사용자) | 로그인 시 발급된 인증 토큰   |
| 통신 암호화(외부 연동)     | 연동처에 발급한 전용 비밀값  |

핵심은 세 가지입니다.

- **용도가 다르면 완전히 다른 열쇠가 나옵니다.** 원본이 같아도 마찬가지입니다.
  따라서 통신용 열쇠가 새어도 저장 데이터는 열리지 않습니다.
- **한 방향으로만 계산됩니다.** 만들어진 열쇠로부터 원본을 역산할 수 없습니다.
- **로그인할 때마다 통신용 열쇠가 새로 만들어집니다.** 열쇠를 오래 고정해 두지 않습니다.

---

## 5) 왜 AES가 아니라 ChaCha20인가

가장 널리 알려진 암호는 AES입니다. 그럼에도 ChaCha20 계열을 택한 이유는 다음과 같습니다.

| 항목            | XChaCha20-Poly1305                       | AES                                 |
| --------------- | ---------------------------------------- | ----------------------------------- |
| 하드웨어 의존   | **없음** — 어떤 장비에서도 일정하게 빠름 | 전용 가속 기능이 없으면 크게 느려짐 |
| 1회용 난수 길이 | **두 배로 확장** — 무작위로 써도 안전    | 짧아서 별도 관리 규칙이 필요        |
| 구현 난이도     | 실수해도 취약해지기 어려운 구조          | 잘못 구현하면 취약해질 여지가 있음  |
| 위·변조 검증    | 방식 자체에 포함                         | 별도 조합 필요                      |

핵심은 **특수한 하드웨어에 기대지 않는다**는 점입니다.
저사양 서버든 태블릿이든 배포 환경이 바뀌어도 성능이 흔들리지 않습니다.
구글이 모바일 통신 기본 암호로 이 방식을 채택한 이유도 같습니다.

또한 저장용 암호화와 통신용 암호화가 **같은 방식 하나를 공유**하기 때문에,
점검할 지점이 하나로 모여 관리와 검증이 단순해집니다.
