# 제품 비교 (배포용)

이 문서는 도입 검토 단계에서 빠르게 판단할 수 있도록, Entity Server를 주요 대안과 비교한 배포 관점 안내입니다.
상세 검증 데이터는 내부 검토 문서에서 관리하고, 여기서는 의사결정에 필요한 핵심 기준만 제공합니다.

## 한 줄 포지셔닝

Entity Server는 **설정 중심 CRUD 백엔드 + 온프레미스 운영 + 보안/이력 기능 내장**에 강한 선택지입니다.

## 운영 모델 비교 (BaaS vs 온프레미스)

| 항목                | BaaS(완전 관리형) | 온프레미스/자체 운영(Entity Server 성향) |
| ------------------- | ----------------- | ---------------------------------------- |
| 인프라 제어         | 낮음              | 높음                                     |
| 초기 구축 속도      | 매우 빠름         | 상대적으로 준비 필요                     |
| 운영 책임           | 공급자 중심       | 팀/조직 중심                             |
| 규제·내부 정책 대응 | 제약 가능성 있음  | 조직 정책에 맞춘 세밀 제어 가능          |
| 커스터마이징        | 플랫폼 범위 내    | 운영/배포/연동 방식까지 폭넓게 가능      |
| 비용 구조           | 사용량 기반 과금  | 인프라+운영 인력 기반                    |

## 유사 제품군 비교

API 기반 백엔드는 공통점이 많지만, **운영 모델과 기본 제공 기능의 우선순위**에서 차이가 납니다.

| 제품군                 | 대표 예시                    | 공통점                          | 주로 강한 영역                       | Entity Server 대비 선택 포인트     |
| ---------------------- | ---------------------------- | ------------------------------- | ------------------------------------ | ---------------------------------- |
| BaaS형 플랫폼          | Firebase, Supabase, Appwrite | API, 인증, 데이터 접근 제공     | 빠른 시작, 관리형 운영               | 인프라를 직접 다루지 않으려면 유리 |
| Realtime/GraphQL 중심  | Hasura, Nhost                | API 자동화, 데이터 모델 기반    | 실시간 동기화, 클라이언트 친화 질의  | 실시간 요구가 핵심이면 우선 고려   |
| CMS/콘텐츠 중심 백엔드 | Strapi, Directus             | API 제공, 권한/콘텐츠 모델 제공 | 편집 워크플로우, 백오피스 UI         | 콘텐츠 운영이 핵심이면 유리        |
| 설정 중심 CRUD 백엔드  | Entity Server                | API 자동 생성, 스키마 관리      | 내부 업무 API, 권한/이력/운영 표준화 | 온프레미스+운영 통제 필요 시 유리  |

## 도구별 비슷한 점 / 다른 점

| 비교 대상           | 비슷한 점                            | 다른 점                                                                                |
| ------------------- | ------------------------------------ | -------------------------------------------------------------------------------------- |
| Supabase / Firebase | API, 인증, 데이터 접근을 빠르게 제공 | 관리형(BaaS) 중심 운영이라 인프라 제어 범위가 상대적으로 제한적                        |
| Hasura 계열         | 스키마 기반 API 자동화               | GraphQL/Realtime 중심 최적화, 운영 기본기는 조합형으로 가져가야 하는 경우가 많음       |
| Directus / Strapi   | API 제공 + 운영 편의 기능            | 콘텐츠/백오피스 워크플로우 중심 강점, 내부 업무 API 표준화와는 우선순위가 다를 수 있음 |
| 전통 ORM 서버       | 도메인 모델 기반 DB/API 구성         | 코드 작성 자유도는 높지만 스키마·권한·이력 운영을 직접 구현해야 함                     |

## 경쟁 제품 비교표 (핵심 기능)

| 기능                       | Entity Server  | Supabase              | Hasura                | Directus              | Firebase           |
| -------------------------- | -------------- | --------------------- | --------------------- | --------------------- | ------------------ |
| API 자동화                 | ✅             | ✅                    | ✅                    | ✅                    | ✅                 |
| 온프레미스 완전 제어       | ✅             | ⚠️ (셀프호스트 가능)  | ⚠️ (셀프호스트 가능)  | ✅                    | ❌                 |
| 다중 RDB 지원              | ✅             | ❌ (PostgreSQL 중심)  | ⚠️ (주로 PostgreSQL)  | ⚠️ (백엔드 DB 의존)   | ❌                 |
| 권한/감사/이력 운영        | ✅ (기본 내장) | ⚠️ (구성 방식에 따름) | ⚠️ (구성 방식에 따름) | ⚠️ (리비전/권한 중심) | ⚠️ (서비스별 정책) |
| Realtime/GraphQL 중심성    | ❌             | ✅                    | ✅                    | ⚠️                    | ⚠️                 |
| 배포 단순성(단일 바이너리) | ✅             | ❌                    | ❌                    | ❌                    | N/A                |

## Entity Server 고유 핵심 기능

| 핵심 기능                                     | 설명                                                 | 실무 의미                                        |
| --------------------------------------------- | ---------------------------------------------------- | ------------------------------------------------ |
| 엔티티 JSON 기반 스키마+API 동시 운영         | 엔티티 정의만으로 테이블/CRUD/API 반영 흐름을 단순화 | 코드 작성량을 줄이고 변경 반영 속도를 높임       |
| 이력·리비전·롤백 내장                         | 변경 이력 추적과 롤백을 운영 기능으로 기본 제공      | 장애/오입력 복구와 감사 대응이 쉬움              |
| 단일 바이너리 중심 배포                       | 서버 구성요소를 단일 실행 단위로 운영 가능           | 배포/업데이트 절차가 단순하고 운영 편차가 줄어듦 |
| 권한 체계 기본 제공 (RBAC/JWT/HMAC/OAuth 2.0) | 인증/인가를 옵션 조합으로 적용 가능                  | 서비스 성격에 맞춘 보안 정책 적용이 쉬움         |
| XChaCha20-Poly1305 암호화 옵션                | 데이터/패킷 암호화를 설정으로 활성화 가능            | 민감 데이터 보호 수준을 높이고 규정 대응에 유리  |
| 확장 기능 옵션형 활성화                       | 파일/SMTP/Push/백업 등을 필요 시 단계적으로 활성화   | 초기 단순 운영 후 요구 증가에 맞춰 확장 가능     |

## 언제 잘 맞나

- 자체 인프라(온프레미스/VPC)에서 운영해야 할 때
- 빠른 API 구축과 운영 표준화(권한, 이력, 롤백)가 필요할 때
- 엔티티 JSON 기반으로 스키마/API 변경을 빠르게 반영하고 싶을 때
- 다중 관계형 DB 또는 일부 NoSQL 스토어를 함께 고려할 때

## 어떤 점이 강점인가

- **설정 중심 개발**: 엔티티 정의 기반으로 스키마/CRUD/API 운영 흐름을 단순화
- **배포 단순성**: 단일 바이너리 중심 배포 모델
- **보안 기본기**: JWT/HMAC/RBAC/OAuth 2.0 및 XChaCha20-Poly1305 기반 암호화 옵션
- **운영 내장 기능**: 이력/리비전, 롤백, 운영 스크립트
- **확장 기능**: 파일, SMTP, Push, 백업 등 옵션형 기능

## 다른 선택지가 더 유리한 경우

- **Realtime/GraphQL이 핵심**인 제품 요구가 강한 경우
- 백오피스 UI/콘텐츠 관리 기능이 핵심인 경우
- 완전 관리형(BaaS) 운영이 우선이고 인프라 제어 필요가 낮은 경우

## 빠른 선택 가이드

- 내부 업무 API, 권한/감사/이력 중요 → **Entity Server 우선 검토**
- Realtime 중심 사용자 앱 백엔드 → Realtime 친화 플랫폼 우선 검토
- CMS/콘텐츠 편집 워크플로우 중심 → CMS형 제품 우선 검토
